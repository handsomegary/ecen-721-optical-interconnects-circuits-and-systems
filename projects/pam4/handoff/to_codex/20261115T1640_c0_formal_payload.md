## 四、主要問題：零偏斜基準本身就退步了

- 同一相位、同一 FFE：
  - 訓練窗：0／176，RMSE 0.185；
  - payload：24／496，RMSE 0.513。
  - 上一輪固定碼診斷的零偏斜（960 符號訓練）是 0／240，RMSE 0.28。
- payload 零偏斜的混淆矩陣（primary）：

  ```
  [[122, 11, 0, 0], [0, 118, 10, 0], [0, 0, 126, 3], [0, 0, 0, 106]]
  ```

  錯誤全部是「判成高一階」，沒有任何判低的情況。secondary 也一樣：`[[116,17,0,0],[0,119,9,0],[0,0,128,1],[0,0,1,105]]`。這是系統性的偏移，不是雜訊或 ISI 造成的對稱錯誤。
- 時間窗的差異：
  - payload：capture TX [128,640)，FFE 中心 [136,632)，第一個讀取在 1.371 ns；
  - training：只在 [448,640) 計分（4.2 ns 以後）。fit 雖然也用 [128,384)，但擬合會把早段的偏移吸收掉，而且早段從來沒有被計分。
- 推測：payload 的前段（約 1.4–4.2 ns）還在電路啟動暫態裡，例如 Vb1 分壓器的 2 pF／RC 或 bias 尚未穩定，造成直流偏移，判決因此一致偏高一階。SWITCH64 量到大跳碼的恢復約 2.5–2.65 ns，這裡從 t=0 起算也在同一量級。偏斜案的錯誤更多，可能是同一個偏移再疊上偏斜的影響。
- 請用保留的 raw 驗證：把 payload 錯誤依時間或符號索引分成早段（<4.2 ns）和晚段（≥4.2 ns）。如果錯誤集中在早段，修正方式是：
  - 讓 payload 計分窗避開啟動段，例如和 training 一樣從 4.2 ns 以後開始，或在前面加 warmup；
  - 或把模擬窗加長，讓 496 個符號全部落在穩定段。
  這樣就不用動相位、選碼或電路。

## 五、建議

- 先處理 payload 窗口。現在 N 晚 primary 沒改善、P 晚錯誤 20%，可能都是窗口問題的副作用，在這之前不適合解讀補償效果。
